Application Architecture:
-------------------------
RockForge.API - Exposes the REST API endpoints and handles incoming HTTP requests/responses.
RockForge.Application - Contains application use cases, business workflows, and service orchestration.
RockForge.Domain - Contains the core business entities, enums, rules, and domain behaviour.
RockForge.Infrastructure - Contains external integrations, in-memory persistence, and technical implementations.
RockForge.Tests - Contains automated tests for critical business rules and application behaviour.

Input Validation:
-----------------
- I created one central validator that exists in the Application layer.
- It throws excpetions for validation errors that bubbles up through 
  the system and by using the excpetions to also cater for validation'
  I set everythin up for Central Excpetion handling later
- No separate message to the user for validation
  Let it all run via the Exception syste,
- API to return only the friendly error to the subscriber
  while the technical(vulnerable) Error data remains internal.
- Foundation laid for Centralised Exception Handling

Category-Validation:
--------------------
- Each category to have its own validation strategy
- Future category should require adding a new class 
  and not modifying existing validation logic,
- Implement Open/Closed Principle
  ~ For a new RockCategory we will create a new strategy
    with it's own interface.
  ~ Register in Program.cs usinf the same Interface(IRockValidationStrategy)
    because the controller request DI to inject using the interface
    DI will inject all the services of that interface...
  ~ New RockCategory will not cause any changes in any existing strategy
    but will be contained in it own strategy
  ~ open for extension, closed for modification.

Global Error Handling:
----------------------
- Let all exceptions come through a central place.
- No try-catches all over the show hiding system errors.
- Standard exception handling and logging
- The fallback 500 is the part that completes the requirement.
  When something genuinely unexpected happens the client must not receive
  stack trace, assembly names, method names, internal paths, SQL details
  Instead they receive the standard problem detail
  {
  "title": "An unexpected error occurred",
  "status": 500,
  "detail": "An unexpected error occurred while processing the request.",
  "instance": "/members/007CTE001/rocks",
  "traceId": "..."
  }
  while the exception is written in the internal log for support developers to fix.
- Final Changes to program.cs.
  
Structured Logging Correlation:
-------------------------------
- Five Logging Rules
  ~ use incoming X-Correlation-Id(or generate one)
    and include it in every log for that request.
  ~ sensible log levels,
  ~ emit structured JSON logs
  ~ log every request outcome including status code and duration
- I chose to use the built-in Microsoft.Extensions.Logging
- Everything logged while that HTTP request is being processed 
  inherits the CorrelationId.
- Each controller, service, validation strategy and 
  the global exception handler do not each have to 
  manually pass the correlation ID around.
- The Correlation Id can be given to Support engineers
  and used find all logs belonging to that particular request.
- Structured JSON logging
  ~ Correlation ID per request
  ~ Correlation ID returned to the caller
  ~ Correlation ID available to every log entry in the request scope
  ~ Status-code-aware log levels
  ~ Request duration logging

Profile Integration Resilience:
-------------------------------
- This is an unreliable external dependency.
  Isolate it, bound how long to wait, retry transient failures, 
  avoid retry storms, log attempts, and preserve partial functionality.
- Endpoint that combines the member's Rocks with 
  the member's profile data from an external/third-party API
- if the third-party API fails
  * require retries
  * exponential backoff with jitter
  * timeout handling
  * retry logging
  * graceful degradation NOT returning a 500 .
- RockForge knows about Rocks.
  RockForge does NOT own profile information.
- When an enriched profile is required
  Then Get Rocks from RockForge
  Then Get profile from external service
  Then Combine them
  Then Return one response
- Resilience: When JSONPlaceholder is down
  * Without resilience external API fails -> RockForge throws exception -> 500 Internal Server Error
    Because some other system is broken, our endpoint is broken.
  * With Resilience -> GET enriched profile -> get Rocks successfully -> call external profile API
                    -> external API fails -> retry a few times -> still fails -> return the Rocks anyway
                    -> enrichmentAvailable = false
- Retry
  * Each retry records Attempt number, Delay Reason, Correlation ID
- Jitter 
  * Rather than hammering the failing service 
    add small random variation to those delays.
- Exponential backoff simply means we wait progressively longer between retries.
- Graceful degradation: could not enrich the response, but I can still fulfil the useful part of the request.
